# IridescentCraft — agent operating brief

Minecraft **1.20.1 Forge** modpack. **This repo is the source of truth:** the live client (PrismLauncher instance) and the dedicated server re-sync to **pushed `main` HEAD**, so a change isn't testable until it's committed **and pushed**.

**Planning/execution split:** if you were spawned for one scoped task, you're an **execution session** — planning happens in a separate session. Do the task, ship it, update `current-state.md`, report back (rule below). If a **design decision** surfaces (gameplay / tiering / dropping a mod / anything non-obvious), **stop and report** rather than deciding it yourself.

**Report back when done (standing rule, operator 2026-10-11):** every execution session ends by sending its close-out to the planning session with `SendMessage`. Find it with `ListAgents`; it is named **"IridescentCraft Dev"**.
- **The report covers:** what shipped (commit hashes) · what was verified and what was NOT · whether it is live on the server · decisions owed by the operator · where the in-game checks are.
- **Fallback:** if the planning session isn't listed, or the send is held or expires (sessions in different permission modes), put the same report at the top of `planning\current-state.md` (you update it anyway) and say so in your final message.
- **Stopping early** (usage limit, blocker)? Report that the same way. An unfinished chip that goes quiet is the failure this rule exists to prevent (2026-10-11: the backups chip sat half-built for five hours unnoticed).

## Standing rules (non-negotiable)
- **Push to `main` automatically right after committing** — solo, direct-to-main, no PR, no review workflow, no asking. Safety = atomic, well-described, revertable commits. Your commits must reach **`origin/main`** (the only ref the live client/server pull); if you're on a spawned worktree branch, push it straight to main. Never `--no-verify`, a scratch branch included.
- **NO `Co-Authored-By` line** on commits.
- **Push the internal repo automatically too** (path below) when you touch it.
- **Commit-first to test:** never hot-edit the PrismLauncher instance or expect an unpushed change to show in-game — the prelaunch sync overwrites it. Roll back by reverting the commit, not by patching the instance.
- **The pre-push hook is installed per clone** (`.minecraft\dev\install-hooks.ps1 -Install`; a worktree uses its clone's hook, and the installed hook is a copy of the template: re-install after the template changes). It runs `Mod-List.md`, the mod index gate, the mod intake gate, the registry snapshot check, the quest validator, the script lints with their ratchet comparison, the engine suite (`run.py fast`), the script load-order and catalogue check (`dev\catalogue`) and `sync-distros.ps1`; most blocks run only when the push touches their files. Blocked on a regenerated `Mod-List.md`? → `git add .minecraft/wiki/Mod-List.md`, commit, re-push. Blocked on a STALE liveness manifest or catalogue? → `node --expose-internals .minecraft\dev\loud\gen_liveness.js`, then `node --expose-internals .minecraft\dev\catalogue\gen_catalogue.js` (in that order), commit what they wrote, re-push. Blocked on `[load-order] FAIL`? → the line names the script and what to change (for an undeclared order, the `// @after` line to add). Every suite by hand: `python .minecraft\dev\engine-tests\run.py all`.
- **The boot-log checker's own test** (`.minecraft\dev\loud\replay-test.ps1`, about 3 minutes) is in no hook: CI runs it after a push to `main` that touches `.minecraft\dev\loud\` (the generated `liveness_manifest.json` included). After such a push read `gh run list --workflow loud-replay-test.yml --limit 3`; a red run is a finding. Run it by hand before pushing a change to the checker itself.
- **A third-party mod is added, updated or removed only through `.minecraft\dev\mods\intake.py`** (`add`, `update`, `remove`; procedure in `.minecraft\dev\mods\README.md`), never by copying or editing a metafile by hand: the pre-push hook and CI refuse a mod with no intake record and a new mod with an open decision. Which mods the pack carries, and every answer to a record's decision, is the operator's: report the record, do not answer it.

## Build & deploy
- **Host gradle is dead** (#39). Build custom mods via each mod's `wsl-build.sh` (WSL2 + JDK17); it deploys to all 3 distro `mods/` and runs the data preprocessors. It never copies to the live server unless asked (since `e9c5a8fe`): only the Tetra expansion's script has a live target, `--live` (distros + the live server) or `--live-only` (the live server only), each after a warning and a 10 s wait — only for a hot fix the operator asked for, never in an execution session, because the server deploys pushed `main` at its policy Cycle. (`--distros-only`, in older notes, is an alias of the default.)
- `iridescent_*` jars are git-ignored artifacts **force-committed** into 3 distro `mods/` + tracked in `custom_jars_manifest.json` (regen after ANY content change, even at the same filename). **Route every jar rebuild/redeploy through the `custom-jar-release` skill** — skipping the manifest regen silently breaks delivery.
- **A custom jar released under a NEW file name** also needs, before the push: the registry snapshot refreshed from the release commit (`boot.ps1 -Ref <commit> -WriteSnapshot`, commit `dev\registry`) and its intake record moved (`intake.py update <mod> <the released jar>`). A rebuild under the same name needs neither.
- **To prove a commit while you keep working:** commit locally, then `powershell -ExecutionPolicy Bypass -File .minecraft\dev\boot\boot.ps1 -Diff <base commit>,<your commit>` (it boots the commits through `git archive`, not the working tree); push when it exits 0 with `REGRESSIONS: 0`.
- **From Git Bash, `powershell -File <script>` needs `-ExecutionPolicy Bypass`:** scripts are disabled on this PC, so without it the script is refused at once (a boot chain 'finishes' in a second). The PowerShell tool already runs with Bypass.

## Layout & testing
- 3 distros: `.minecraft\mods` · `.minecraft\server_distribution\` · `.minecraft\distribution\client\`. `sync-distros.ps1` mirrors `kubejs/{startup,server}_scripts`, `kubejs/assets`, `kubejs/data`, `config/paxi/datapacks`, the cleanup script (incl. the server-runtime seed copy), and gates manifest parity — mod configs and mods/ remain per-distro (configs legitimately differ; mods are packwiz/custom-jar managed).
- The operator runs in-game tests. When handing one off, give **paste-ready** `/give` `/summon` `/locate structure` `/tp` commands with **real IDs** looked up from the scripts/datapacks (don't guess); flag cosmetic-only breakage (e.g. a missing lang key) so they know the behavior still validates. An operator command (`requires(hasPermission(2))`: `/icraft despawn`, `/icraft live`, `/icraft mana_debug`) needs a tester with operator status; the live server's `ops.json` is empty on purpose.

## Scripts (KubeJS)
- **Writing or changing a script:** the conventions are `.minecraft\kubejs\README.md` (short) and `dev\script-conventions.md` in the internal repo (in full). Which script owns an event, sets a global or registers a feature, and in which order an event's handlers run: `.minecraft\dev\catalogue\CATALOGUE.md` (generated; read it before grepping 160 server scripts). A new script starts from `.minecraft\dev\catalogue\script_template.js`; the hook checks its header fields.
- **Load order:** only the guard (1000), the server libraries (900 to 840) and the liveness summary (-1000) carry a `// priority` line; a feature script never gets one. An order between two feature scripts is `// @after <path>  <why>`; a handler that must be the last of its event is `// @last <event>`. Neither moves a script: the check holds the order the file names give.
- **A hurt handler** is `global.icraft.core.onHurt(key, fn, who, options)` (or `onHurtLate`), never a registration on the Java damage registry (lint DIRECT-HURT-REG). The options `place`, `secondary`, `cancelled`, `unchecked` and the list `PLACED` in `0_lib_core.js` exist for the handlers moved off that registry: adding one to a handler, or taking one off, changes damage numbers and needs a decision and the hit table (`python .minecraft\dev\engine-tests\lib\hit\record.py`, then read the diff of the golden file).
- **Prove behaviour per site:** moving a script onto a core helper, or making a silent catch report, is proven per site before it ships (a suite, a golden snapshot, or a probe on a full-pack boot). A site that would wake a feature that never ran is left as it is, marked, and goes to the decision list; repairing a test that never ran is measured over every entity type (or item) the game has before it ships.

- The public wiki **auto-syncs via the `sync-wiki.yml` GitHub Action** on push to `main` (runs `sync-wiki.py`, which also does pack→flat link conversion). **Do NOT manually push the `IridescentCraft.wiki` clone** — it's redundant and produces broken wiki links.
